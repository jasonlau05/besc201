=== PDF PAGE 7 ===
Common file systems in Linux
• ext4 (Fourth Extended File System):  Default in Ubuntu, Debian.
• massive storage drives
• uses journaling to protect data against sudden power cuts or system crashes.
• Btrfs (B-tree File System): Default for Fedora and openSUSE. 
• "copy-on-write" features, allowing users to take instantaneous system snapshots
• easily pool multiple drives together
• repair data corruption automatically.
• XFS: Default file system for RHEL and CentOS
• highly scalable and optimized for massive servers, heavy parallel workloads, and giant files.
• ZFS (OpenZFS): integrated natively into Ubuntu Server options
• A powerful file system and logical volume manager combination favored by system administrators for 
storage servers 
• “unmatched” data integrity protection, built-in RAID features, and aggressive data compression.
• tmpfs: A specialized, temporary file system that runs entirely in the computer's volatile RAM 
memory.

A DETAIL ED EXAMPLE
Appending one block means three separate 
writes
I[v2]: the inode
Must point to the new block 5 and 
record the larger size, now 2 blocks.
B[v2]: the data bitmap
Marks the new data block as 
allocated.
Db: the data block
The user’s new contents, written into 
block 5.
These writes sit in the page or buffer cache for seconds, so a crash can strike before, between or after them.

CRASH SCE NARIOS
Which writes reached disk before the crash?
Writes that reached disk Resulting state
Only Db No problem: no inode or bitmap says the block is in use
Only I[v2] Inode points to garbage in block 5; bitmap says it is free
Only B[v2] Space leak: block 5 is marked used but no inode points to it
I[v2] and B[v2] Metadata consistent, but block 5 holds old garbage data
I[v2] and Db Inode points to block 5, but the old bitmap still shows it free
B[v2] and Db Block in use, but no inode says which file owns it

THE  CO NSISTENCY -UPDAT E PROBLE M
The disk commits one write at a time
Ideal
Move the file system atomically from 
one consistent state to another: all 
three writes happen, or none do.
Reality
The disk services one request at a 
time, and a crash can land between 
any two of them.
Symptoms
Inconsistencies, space leaks, and 
garbage data returned to users.
This is the crash-consistency problem, also called the consistent -update problem.

SOL UTION 1 : THE FILE SYSTEM CHECKER
Let inconsistencies happen, then repair them 
at boot
Check What fsck verifies
Superblock Sanity checks, such as file system size versus blocks allocated; may fall back to a copy
Free blocks Scans inodes and indirect blocks to rebuild which blocks are really in use
Inode state Each inode has a valid type; corrupt inodes are cleared and their bitmap bits updated
Inode links Link counts match the number of directory references found by a full tree walk
Duplicates and bad blocks Two inodes claiming one block; pointers outside the valid range are removed
Directories “.” and “..” come first, and each directory is linked from exactly one parent

=== PDF PAGE 34 ===
DATA  J OURNALING
The transaction: a begin block, the updates, 
and an end block
TxB I[v2] B[v2] Db TxE
1. Journal write
Write TxB, the final addresses and contents, and TxE to the 
log. Wait for these writes to finish.
2. Checkpoint
Write I[v2], B[v2] and Db to their final on -disk locations. Once 
that completes, the update is done.
Physical logging stores exact block contents; logical logging stores a compact description of the change.

=== PDF PAGE 35 ===
A SUBTL E PROBLE M
The disk may reorder writes, so TxE can land 
too early
TxB I[v2] B[v2] ?? missing TxE
The danger
The transaction looks valid, so recovery replays it and copies 
garbage into the live file system, possibly over the 
superblock.
The fix
Issue the journal write in two steps: everything except TxE 
first, wait, then TxE. Costly, since each wait is a rotation.
Better: put a checksum in TxB and TxE, so one write covers the whole transaction. Linux ext4 uses this.

=== PDF PAGE 36 ===
THE  DAT A JOURNAL ING PR OTOCOL
Three phases, and recovery is a replay
1. Journal write
TxB, the contents, and metadata go to 
the log. Wait for them.
2. Journal commit
Write TxE. The transaction is now 
committed.
3. Checkpoint
Write the update to its final locations in 
the file system.
Crash before commit
Skip the pending transaction. Nothing changed on disk.
Crash after commit
Replay committed transactions in order: redo logging. Replaying 
twice is harmless.

=== PDF PAGE 37 ===
BATC HING AND A FINITE L OG
Batch many updates, and reuse the log as a 
circle
Global transactions
Creating file1 and file2 in one directory dirties the same inode 
bitmap, inode block and directory block. Buffer them into one 
transaction, so each block is written once.
Circular log
Once a transaction is checkpointed, free its space. A journal 
superblock records the oldest and newest live transactions.
1. Journal write 2. Journal commit 3. Checkpoint 4. Free
Writing each data block twice is costly. The next slides address that.

=== PDF PAGE 38 ===
META DATA JOURNAL ING
Log only metadata, and write data before it
Data journaling
Every user block goes through the log, so most traffic is 
written twice and sequential writes run at about half 
bandwidth.
Ordered (metadata) journaling
Only metadata goes to the log. Data is written to its final 
place first, so no committed pointer can reach garbage.
Protocol: data write, journal metadata, journal commit, checkpoint metadata, free.
ext3 offers data, ordered and unordered modes. NTFS and XFS use some form of metadata journaling.

=== PDF PAGE 39 ===
A TRICKY CASE
Block reuse: a deleted directory’s block 
becomes a file
1. Journal foo’s directory
Metadata journaling logs the directory 
block 1000 for foo, while file data is 
not journaled.
2. Delete foo, reuse block 
1000
Create bar, whose data lands in block 
1000. The new data is not journaled, 
so the log still holds the old directory 
contents.
3. Replay overwrites bar
Recovery replays the old directory 
block over the file bar’s data, a 
serious and surprising corruption.
Fix: a revoke record in the log tells replay to skip earlier entries for that block. ext3 does this.

=== PDF PAGE 40 ===
SOL UTION 3:  OT HER APPROA CHES
Order the writes, or never overwrite in place
Soft updates
Order every write so structures never 
point to garbage. Hard to implement 
correctly.
Copy-on-write
Write new versions to unused locations, 
then flip the root pointer. ZFS uses this.
Backpointers
Each block records its owning inode. A 
mismatch on read reveals an 
inconsistency, with no ordering needed.
Optimistic crash consistency reduces how often the journal must wait for disk writes, given a more capable disk interface.
