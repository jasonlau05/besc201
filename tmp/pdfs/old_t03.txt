One-to-one
• Each user-level thread maps to kernel thread
• Creating a user-level thread creates a kernel thread
• More concurrency than many-to-one
• Number of threads per process sometimes restricted due to 
overhead
CSCE 410 Fall 2026 7

=== PDF PAGE 8 ===
Many-to-One
• Many user-level threads mapped to single kernel thread
• One thread blocking causes all to block
• Multiple threads may not run in parallel on multicore system 
because only one may be in kernel at a time
• Few systems currently use this model
CSCE 410 Fall 2026 8

=== PDF PAGE 9 ===
Many-to-Many
• Go goroutines are not many-to-one. 
Go uses an M:N scheduler, multiplexing many goroutines over 
multiple OS threads. 
• Modern Java virtual threads are not simply many-to-one; the 
runtime schedules many virtual threads over a set of 
carrier/platform threads.

Pthreads
• May be provided either as user-level or kernel-level
• A POSIX standard (IEEE 1003.1c) API for thread creation and 
synchronization
• Specification, not implementation
• API specifies behavior of the thread library, implementation is up 
to development of the library
• Common in UNIX operating systems (Linux & Mac OS X)

Thread Pools
• Create a number of threads in a pool where they await work
• Advantages:
• Usually slightly faster to service a request with an existing thread than create a new 
thread
• Allows the number of threads in the application(s) to be bound to the size of the pool
• Separating task to be performed from mechanics of creating task allows different 
strategies for running task
• i.e.,Tasks could be scheduled to run periodically

Threads in GPUs: CUDA
In 2006, NVIDIA introduced CUDA, which originally stood for “Compute 
Unified Device Architecture” , a general-purpose parallel computing platform 
and programming model that leverages the parallel compute engine in 
NVIDIA GPUs to solve many complex computational problems in a more 
efficient way than on a CPU.
• The CUDA parallel programming model has three key abstractions at its 
core:
• a hierarchy of thread groups
• shared memories
• barrier synchronization
• A kernel is executed in parallel by an array of threads
• All threads run the same code
• Each thread has an ID that it uses to compute memory addresses and 
make control decisions

CPU vs GPU threads
CPU threads GPU threads
Usually tens of runnable threads Often thousands or millions
Relatively heavyweight Extremely lightweight
Each has substantial execution state Small per-thread state
OS schedules kernel threads GPU hardware/runtime schedules threads
Optimized for general control flow Optimized for massive data parallelism
Context switching is relatively expensive Hardware rapidly switches among groups of threads
Threads can execute quite independently Threads execute in groups, such as NVIDIA warps or AMD wavefronts

=== PDF PAGE 19 ===
GPU vs OS threads
• GPU threads are not OS threads.
Creating 100,000 CUDA threads does not create 100,000 kernel threads. 
They are lightweight execution contexts managed by the GPU programming 
model and hardware. 
• Threads are organized hierarchically: grid → thread blocks → threads
• A kernel launch might conceptually say, "Run this function 1,000,000 times, 
once for each element. " The programmer describes enormous parallelism 
and lets the GPU map it onto the available hardware.
• SIMT execution changes the meaning of independent threads.
NVIDIA GPUs execute threads in groups called warps (typically 32 threads). 
Threads have their own registers and logical state, but the hardware 
schedules execution at warp granularity.
• Scheduling is used to hide latency.
• Synchronization and memory hierarchy matter.
